ordered by when they become relevant, not by priority alone.

## 2. Ethiopian egress for Telebirr in production (launch blocker)

Telebirr's receipt host refuses TCP from outside Ethiopia (verified: DNS
resolves, connect times out). Before launch, pick one:

- (a) host verification workers on a VPS with an Ethiopian IP in-region;
- (b) route Telebirr (and any other geo-blocked) adapter calls through an Ethiopian proxy/relay;
- (c) negotiate direct API access with Ethio Telecom.

Determines whether Telebirr verification can work in production at all.

## 3. Dashen auth API fallback (future phase)

The multi-endpoint HTTP adapter (13D.4) is the MVP "partial-verification"
path. A full verification path for Dashen needs their receipt-check API,
which requires credentials the project does not have yet.

## 4. `@nestjs/axios` retry tuning (deferred)

Decide whether adapter HTTP calls should retry at the axios/HTTP layer in
addition to AdapterBase's retry-with-backoff. Base-class retries already
bound total attempts; an extra layer risks multiplying requests against
flaky bank endpoints.

## 5. PDF fixture quality audit (13D.6+7 follow-up)

M-Pesa and Zemen PDF fixtures are synthetic (generated by
[backend/scripts/generate-pdf-fixtures.mjs](../../backend/scripts/generate-pdf-fixtures.mjs));
they validate the parser logic but not the real-world layout variations
(font subset extraction, multi-line field values, RTL/Ethiopic text).
Once one real M-Pesa or Zemen PDF is available from a live endpoint,
replace the synthetic fixtures with sanitized real ones and re-run the
two parser suites.

## 6. Fix `npm run export:error-codes` (13E.1 follow-up)

The script execs `src/scripts/export-error-codes.ts`, which does not
exist — it has never run. Until it does, the
[shared/contracts/error-codes.json](../../shared/contracts/error-codes.json)
mirror is maintained by hand and can silently drift from
[error-codes.ts](../../backend/src/common/constants/error-codes.ts).
Small fix: write the script (read ERROR_CODES, group by prefix, write
the JSON).

## 7. CI check: error-codes.json mirror sync

Depends on item 6. Once the export script exists, add a CI check that
regenerates the mirror from the TS constants and fails on diff — a
hand-maintained mirror WILL eventually drift otherwise.

## 8. BullMQ dead-letter dashboard / admin retry UI (13E.3 follow-up)

Failed verification jobs stay in Redis for 24h (`removeOnFail: { age: 86400, count: 5000 }`). Until an ops surface exists,
failed jobs are visible only via Redis tooling, and manual retries go
through the merchant `/verifications/:id/retry` endpoint (13E.3). For the
ops dashboard (Step 28): a queue view listing failed jobs with their
verificationId + errorCode, and a one-click re-enqueue. Trigger: after the
first real dead-letter batch in production.

## 9. Remaining SET NULL FKs vs immutable-ledger rules (13E.3 finding)

Migration 20261025000000 fixed the two verification-facing FKs on
`credit_transactions` (SET NULL → RESTRICT): `ON DELETE SET NULL` FK
actions issue UPDATEs that the `credit_tx_no_update` rule rewrites, making
EVERY parent-row delete abort even with zero referencing rows. The same
trap still exists for the other SET NULL FKs into rule-protected tables:
`credit_transactions.subscription_id`, `credit_transactions.actor_user_id`,
and any FK pointing at `audit_logs`. Decision needed when subscription or
user hard-delete flows land (users are soft-deleted today): convert the
FKs to RESTRICT, or accept that referenced rows are hard-delete-immutable.
