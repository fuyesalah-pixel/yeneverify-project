## 9. Remaining SET NULL FKs vs immutable-ledger rules (13E.3 finding)

Migration 20261025000000 fixed the two verification-facing FKs on
`credit_transactions` (SET NULL → RESTRICT): `ON DELETE SET NULL` FK
actions issue UPDATEs that the `credit_tx_no_update` rule rewrites, making
EVERY parent-row delete abort even with zero referencing rows. The same
trap still exists for the other SET NULL FKs into rule-protected tables:
`credit_transactions.subscription_id`, `credit_transactions.actor_user_id`,
and any FK pointing at `audit_logs`. Decision needed when subscription or
user hard-delete flows land (users are soft-deleted today): convert the
FKs to RESTRICT, or accept that referenced rows are hard-delete-immutable.

## 13. Per-run queue isolation for e2e suites (14.2 finding)

Every e2e suite booting the app registers a VerificationProcessor on the
SHARED BullMQ queue. Under parallel jest workers a suite whose worker has
no matching OCR fixtures can steal another suite's jobs and produce ERROR
verdicts (observed twice on 2026-10-27). Mitigated by running e2e serially
(`test:e2e` uses `--runInBand`). Proper fix: derive the queue name per
suite/run (e.g. env-suffixed QUEUE_NAMES) so suites can run in parallel.
Trigger: e2e runtime becomes annoying enough to want parallelism.

Third variant (Step 15, 2026-10-28): a stuck/jacked-up jest process from
an earlier session kept running hours later and stole jobs from e2e runs
while having no fixtures registered (silent VERIFICATION_BANK_NOT_DETECTED
on otherwise-VERIFIED suites). Diagnostics that pointed the wrong way:
solo suite runs passed, full runs failed, and the DB row looked intact.
Rule of thumb after an agent session ends: before trustng a "suite failed
in full run, passes solo" flake, list running jest/node processes — a
stale one is a job thief. (`Get-CimInstance Win32_Process -Filter
"Name='node.exe'"` and kill the stale `jest` PIDs.)

## 14. OTP rate-limit counters are cross-run e2e state (14.2 finding)

The Redis-backed OTP limiter keys on phone, IP, and phone+purpose with
hourly/5-min windows; repeated e2e runs exhaust the shared `otp:ip:*`
budget and whole suites start 429ing. Mitigated by a beforeAll reset
helper (`test/reset-otp-rate-limits.ts`) in OTP-touching suites. Trigger:
if production relies on the same limiter, make sure the per-IP cap is
tuned for shared egress (offices/NAT) before launch.

## 15. Adapter regex audit — hex-only truncation (DONE, 14.3 Part A)

14.2 found a hex-only regex in the e2e stub fixture (`/TK[0-9A-F]+/`
truncated `TKFAKE…` to `TK`, mislabeling FAKE as VERIFIED). Audited
all 7 real adapters as part of 14.3: **0 of 7 use hex-only patterns** —
every `extractReference` delegates to the shared
[reference-patterns.ts](../../backend/src/verification/regex/reference-patterns.ts)
map, whose shapes are all `[0-9A-Z]` (case-insensitive; M-Pesa is
uppercase-only by receipt format). Edge-case tests asserting G-Z letters
survive extraction added per adapter. Trigger to reopen: any new adapter
introducing a local (non-shared) reference regex.

## 16. Document "verdict commits before consume" for Step 15+ clients

Architectural fact, not a bug: the processor writes the VERDICT first,
then the consume commits in its own transaction. A client that polls the
verification status and then immediately reads the credits balance can
observe the charge a few ms late. Document for the Flutter step (Steps
20+): after a terminal status, read the balance with a short retry window
(200–500 ms) or render a transient loading state on the credits line.
The e2e suites handle this by polling the balance until it settles.

## 20. Evaluate time-staged credit delivery for multi-month prepayments (Step 17 addition)

Current MVP rule: each approved billing grants the package's credit
allotment immediately, regardless of timing (two BUSINESS payments in the
same month = 800 credits, subscription expiry still extends +30d per
payment). Alternative models:

- (a) stage per-month credits: grant 400 now, 400 when the second month starts (needs a scheduler);
- (b) extend the subscription without adding credits (current-ish, but credits never stack);
- (c) keep the MVP rule (credited immediately — merchant-friendly, simplest ledger).

Decide based on real merchant behavior post-launch; refund/void policy for
over-granting is part of the same decision. Trigger: first multi-payment
month for the same merchant.
